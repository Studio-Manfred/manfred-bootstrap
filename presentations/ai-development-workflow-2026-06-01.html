AI doesn't write my code.
It follows my process.

How I ship AI-built software I actually trust — at speed.

Open here, not on a title card. The whole talk is unpacking this one sentence. Set expectation: this is my real day-to-day workflow, not a product pitch. ~45–60 min, one live walkthrough at the end. For an external/client room: I'm here to demystify, not to sell. By the end you'll see AI-assisted dev as disciplined, not magic.

The tension in the room

The fear

Sloppy code. Hallucinated APIs. Untested output you can't trust. "It works on my machine, once."

The promise

Ship a feature end-to-end in an afternoon — design, tests, CI, deploy — without cutting corners.

Both are real. The gap between them is discipline — and discipline can be written down.

Name what people actually feel. Most have either tried AI coding and got burned, or are scared to. The thesis: the difference between the fear and the promise isn't the model — it's the process around it. And process is portable.

Why the naive way breaks

Prompt → paste → hope

  • No memory. Every chat starts from zero. Yesterday's decisions are gone.
  • No tests. "Looks right" is the only check. Nothing catches the regression next week.
  • Unexamined assumptions. The model builds what you said, not what you meant.

Fast to a first draft. Slow to anything you'd put in front of a user.

This is "vibe coding." It's genuinely useful for throwaway prototypes — and a trap for real software. The three failures map directly to the three fixes I'll show: memory (written process + knowledge base), tests (TDD), assumptions (brainstorming gate).

The shift

Treat the AI as a disciplined teammate — not autocomplete.

The point isn't that it types fast.

It's that the rules of how we work are written in files it reads every single session.

The reframe. A new teammate who's brilliant but has amnesia each morning — what do you give them? An onboarding doc, a definition of done, and notes from past mistakes. That's exactly what the next slide is. The cleverness is in the setup, not the prompt.

The whole trick in three files

FileRoleRead
AGENTS.md"This is NOT the framework you assume" — guardrails read firstTop of every session
CLAUDE.mdThe operating manual — stack, conventions, the definition of doneEvery session
MEMORY.md~50 one-line learnings — gotchas and decisions that bit me onceRecalled by relevance

Write the process where the AI reads it. Everything else is detail.

If they remember one slide, this is it. These are plain markdown files committed to the repo. AGENTS.md is tiny on purpose — e.g. "this project is Vite + React, NOT Next.js" — because the model's default assumptions are the #1 source of wrong code. MEMORY is the compounding part: the system gets better at MY projects specifically, because the learnings live where it looks.

The pipeline

Idea → ship → learn

💡 Idea → 🧠 Brainstorm → 📋 Plan → 🎫 Ticket → 🌿 Branch
→ 🔴 Failing test → 🟢 Code → ♻️ Refactor + docs
→ ⬆️ PR → 🤖 CI (verify · e2e · edge) → ▲ Vercel preview
→ 🔀 Squash-merge → 🚀 Auto-deploy → 📝 Save learnings ↺

It's a loop. The last step feeds the first.

Don't read every box — point to the shape. Most of this is the same loop any good team uses; the difference is the AI runs it WITH me, holding the discipline. I'll zoom into three moments next, then show the whole loop running live on one real feature. Gloss the jargon now: "ticket" = a work item in Linear (our tracker); CI = automated checks on every change; Vercel = where it deploys.

Moment 1

It starts with a question, not code

There's a hard gate: no code until the design is approved. The AI explores the codebase, then asks me one question at a time and proposes 2–3 options.

Real moment: I asked it to brainstorm a shared footer across apps. It explored, found there was no footer yet, and asked "what actually varies per app?" before proposing anything. I said "I'll wait" — and it stopped cleanly. Nothing created.
The most expensive bugs are unexamined assumptions. Five minutes of questions beats an afternoon building the wrong thing. The "it stopped cleanly" detail matters for a client audience worried about runaway AI — restraint is a feature. It does what's asked and no more.

Moment 2

The ticket exists before the branch

Every piece of work gets an ID first — STU-501. That ID is the join key between the code and the tracker.

Branch  feat/stu-501-…
Commit  feat(search): … (STU-501)
Test    describe('… (STU-501)')
PR      Closes STU-501

Search the code for STU-501 → every file it touched. Search the tracker → every commit and PR. One thread through both systems.

Linear = the issue tracker; STU = our project prefix. The discipline: no free-form TODOs that go stale and lose owners — everything is anchored to an ID. This is what makes the work auditable months later. It also means the PR auto-closes the ticket on merge — no manual bookkeeping.

Moment 3

A failing test is the best prompt you can give an AI.

A precise red test says exactly what "done" means — far better than a paragraph of English. The AI's job becomes simple: make it green.

This is the pivot into TDD. The insight for the room: English is ambiguous, a test is not. When I write the test first, I've specified the behaviour precisely, and the AI can't drift. It also flips the trust problem — I'm not trusting AI-written code, I'm trusting a test I wrote and watched fail.

Test-driven development, with AI

Red → Green → Refactor

🔴 Red

Write one failing test. Watch it fail for the right reason.

🟢 Green

Simplest code that passes. Nothing more.

♻️ Refactor

Clean up while staying green.

The tactic: extract a pure helper — don't test the 1,000-line page.

Lift the logic into a small function, prove that. The component just wires it.

"Watch it fail" is non-negotiable — a test written after the code passes immediately and proves nothing. Our pages are huge and hard to test, so I don't fight them. I move the brain (the logic) into a tiny tested function and leave the dumb wiring in the component. You'll see this exact move in the demo.

Match the test to the risk

The testing pyramid

LayerCatches
Deployed-smoke (UI)"Does it actually work on the real deploy?"
E2E (Playwright)Whole flows — login, boards, search — desktop + mobile
Accessibility (axe)Keyboard + screen-reader regressions
Integration + UnitLogic, reducers, validators — fast, hundreds of them
Static (lint)Issues at edit time, before a test even runs

No visual-regression snapshots — high maintenance, low signal for us.

Bottom-heavy on purpose: hundreds of fast unit tests, a handful of slow end-to-end ones. Each layer answers a different question. Pure logic → unit. Wiring → E2E against a fake backend. "Is it really live" → smoke against the real Vercel preview. Coverage is guarded by a ratchet that can only go up — more on that shortly.

Not an afterthought

Accessibility is built in

  • axe sweeps every rendered page in the test run.
  • ARIA wired into every interactive feature — the search panel announces its highlighted result to screen readers.
  • WCAG 2.2 AA as the baseline, with dedicated a11y skills carrying the rules.

Default soft, then ratchet to strict — one rule at a time.

For a client audience this is a trust signal: accessibility isn't a nice-to-have we add at the end, it's in the test suite and the definition of done. The "warn then enforce" pattern lets a big existing codebase improve without one giant blocking cleanup — every fix permanently tightens one rule.

Multi-agent orchestration

Many agents, one judge

Parallelism for coverage

Several agents sweep different parts of a problem at once, each blind to the others.

Skeptics for confidence

One agent finds a claim; separate agents try to refute it. Only survivors get reported.

A finding that survives three skeptics is worth more than one a single agent asserted.

I can run a fleet of sub-agents for breadth, then have them check each other adversarially for depth. This is how the security review works. Key governance rule: sub-agents return data; one orchestrator makes the judgement calls. I don't let ten agents all scribble notes — the decisions stay in one place.

Security

Guard at the chokepoint, lock it with a test

  • One sanitiser all rendered HTML must pass through — then one regression test that can't be bypassed.
  • Secrets never reach the browser — anything sensitive lives server-side, by rule.
  • Security policy as enforced code paths, not a checklist someone reviews by eye.

Plus a periodic adversarial review that confirms the fixes stayed fixed.

The principle: one guard at the single point everything flows through beats reviewing every call site by hand. Add a test and it can never silently regress. Example without jargon: any user-written content that becomes HTML on a page is force-cleaned at one function, and a test proves a malicious payload gets stripped.

CI & deploy

See it on real infra before it merges

Open PR → 🤖 checks run automatically
  verify (lint · tests · coverage · build)
  e2e (browser, desktop + mobile)
  edge (backend functions)
→ ▲ Vercel builds a live preview URL for that PR
→ green ✅ → merge → 🚀 production

Every change gets its own working URL. I watch it run before I trust it.

CI = continuous integration: a robot runs all the checks on every change. Vercel = our hosting; it spins up a real, shareable preview of each PR. That preview is the moment that pays off most — I (or a client) click through the actual change on real infrastructure before anything merges. No surprises in production.

Make quality irreversible

Ratchets only tighten

Coverage

Test coverage can only go up. A drop fails the build.

Warn → enforce

Each fix flips one rule from warning to blocking. Permanently.

Lock-the-fix

Ship the regression test before the fix; the day it passes, it's locked green.

"We'll fix it later" becomes a mechanism, not a hope.

Big existing codebases have debt. Ratchets turn cleanup into a one-way valve — things can only get better, never quietly regress. This is how you bring AI velocity to a messy real codebase without the mess growing back.

STU-501 · the loop in action

Ticket → branch → 🔴 → 🟢

The feature was "arrow keys move a highlight." So I extracted the logic — not the giant component — and tested that first:

// src/lib/search-keyboard-nav.ts  — pure, testable
export function nextActiveIndex(current, key, length) {
  if (length === 0) return -1
  if (key === 'ArrowDown') return current >= length - 1 ? 0 : current + 1
  if (key === 'ArrowUp')   return current <= 0 ? length - 1 : current - 1
  return current
}
// 9 tests written first → watched them fail → made them green
Walk the move: the brain of the feature is this tiny function — wrap at both ends, handle "nothing selected." I wrote 9 tests for it before the function existed, watched them fail (the file didn't even import), then implemented until green. The search component just calls this on each keypress. The hard part is proven in isolation; the wiring is trivial.

STU-501 · proving the test is real

Proven by deletion

I wrote 3 end-to-end tests for the keyboard flow. To prove they actually test the feature, I put the old code back and reran them:

Old code → 3 failed ✗  ·  my code → 3 passed ✓

If a test passes against the broken version, it isn't testing anything.

This is the discipline most people skip. A green test only means something if you've seen it go red. I swapped the pre-feature file back in, rebuilt, watched all three fail, then restored mine and watched them pass. For the room: this is why I trust AI-written code — not because the AI is smart, but because the safety net is verified.

STU-501 · close the loop

Green → merge → learn

Shipped

224/224 tests green · coverage ratchet held · CI verify + e2e + edge all ✓ · squash-merged · ticket auto-closed.

Learned

Saved one reusable note: "copy this keyboard-nav pattern for any future menu / autocomplete."

Next time I build an autocomplete, that pattern is one recall away.

The numbers are real from the session. The point isn't the count — it's that the whole loop ran with the discipline intact, and merging was a non-event because everything was already proven. The learning step is the compounding flywheel: the system is now permanently a little better at my work.

Trust cuts both ways

When the review is clean, it says clean

I ran a full security review of the codebase with adversarial agents. The result: no exploitable issues.

So I filed nothing.

It did not invent findings to look busy. A clean review reports clean — that's what makes the non-clean ones credible.

I'd asked it to file findings as tickets. It found none and told me so, instead of manufacturing noise. I confirmed and we filed nothing. For a client audience this is the trust close: the system's "all good" is believable precisely because it's willing to say "all good" — and willing to stop, and willing to ask.

If you take five things home

  1. Write the process where the AI reads it — not in clever prompts.
  2. A failing test is the best prompt.
  3. One ID threads idea → code → tracker.
  4. Guard at the chokepoint, lock with a test.
  5. Every session improves the knowledge base.
Slow down here — this is the transferable payload. None of these are tool-specific; they work with any AI assistant, any stack. Invite them to map each to their own context as I read them.

The human stays in control

What the AI must ask before it acts

✅ Does on its own

Branch, test, code, open a PR, auto-close a ticket via the PR.

🛑 Must ask first

Comment in the tracker · rewrite risky logic · force-push · fabricate a finding · publish anything outward.

Autonomy on the reversible. A human nod on the rest.

Pre-empt the fear directly: this isn't an agent running wild. The boundary is reversibility — it moves fast on things easily undone, and stops to ask on anything outward-facing or hard to reverse. That boundary is itself written in the process files, so it holds every session.
